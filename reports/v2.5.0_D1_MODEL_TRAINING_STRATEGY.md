# Taksh v2.5.0-D1 — Model & Training Strategy Assessment

Date: 2026-11-06
Mode: research, analysis and recommendations only
Status: **D1 assessment complete; no implementation authorized**

> This report does not authorize a model, dataset, training run, checkpoint conversion, purchase, publication, license decision, or release. Client execution artifacts from earlier AD-1 work are outside this repository and are not evidence of product capability.

---

## 1. Executive recommendation

**Recommendation: `DUAL-TRACK STRATEGY`.**

- **Taksh Research** should continue as the from-scratch Llama-style research line. It is the only path that preserves the repository’s independence and its existing training/benchmarking infrastructure. Its near-term role should be scientific and diagnostic, not the product default.
- **Taksh Code** should be based on a replaceable, legally compatible pretrained coding model with an adapter/provider abstraction. It should not silently replace the from-scratch model.

The practical first product foundation is **Seed-Coder-8B-Instruct** under MIT, with **Qwen2.5-Coder-7B-Instruct** under Apache-2.0 as the close alternative. **Qwen3-Coder-30B-A3B-Instruct** is the stronger newer Apache-2.0 candidate, but it requires hosted or high-end GPU inference and should be treated as a reference/oracle model, not the first local fine-tuning target.

Rationale:

1. The Taksh S2 model has no measured general coding capability: AD-1 raw exact is still **2/29**, and the new C3 held-out benchmark produced **0/54 exact, 0/54 binding, and 0/45 functional fixtures**. Continued from-scratch work alone has no plausible path to a practical coding product on the current budget.
2. The foundation-model sources analyzed here are legally usable if license-specific obligations are honored. Apache-2.0 and MIT are the cleanest; DeepSeek and StarCoder2 are usable only with use-based restrictions that propagate to derivatives.
3. The host can support a small GGUF feasibility probe but not a useful local 7B/8B workhorse; a GPU or hosted path is required for product-grade inference.
4. A dual track preserves the sovereign-research value while avoiding a binary bet that the current 9.36M checkpoint can be trained into a coder without a major data and hardware investment.

This is not a claim that any listed foundation already meets Taksh product gates. It is an assessment of the most viable route to reach those gates.

## 4. Hardware and cost analysis

### Assumptions

- Weights are held locally as safetensors/BF16 for training and converted/served as GGUF only after separate authorization.
- Inference memory below assumes about **0.55–0.75 GB of GGUF weight memory per billion parameters** plus KV cache and runtime overhead.
- Long context increases KV cache sharply; 8K–32K coding contexts are more expensive than a short 512-token benchmark.
- Costs below are **planning estimates, not quotations**. Cloud pricing varies by provider, region, reserved capacity and output volume.

## 5. Training and dataset strategy

### Existing corpus

The current `code_corpus_v1` has **447 records / 2,277,473 tokens**, which cannot train a credible general coding model. The repository’s 100M-token design target and the estimate of roughly 100B tokens for a 100M model make clear that the current corpus is a pipeline artifact, not a capability dataset.

Reusable items:
- Existing JSONL/manifest structure.
- Provenance fields.
- `data/contracts/` and licence-gate patterns.
- Benchmark isolation and frozen-suite tooling.
- Held-out benchmark construction discipline.

Items requiring replacement or major expansion:
- C# corpus: no cleared acquisition yet.
- Python-first corpus: only 2.28M tokens.
- JS/TS expansion: no material evidence in the measured corpus.
- Model-weights/training-data license: absent.
- Human-eval-grade functional corpus: no Taksh-specific executable benchmark beyond the narrow AD-1/C3 suites.

### Required dataset policy

Before any download:

1. Record source URL, pinned revision, retrieval date, licence source, licence text hash and reviewer.
2. Exclude sources whose licence text conflicts with metadata.
3. Deduplicate by content and file path, not only by approximate token overlap.
4. Separate repository, commit and file groups so one repository cannot span train and evaluation sets.
5. Benchmark contamination checks must include published HumanEval, MBPP, SWE-bench and repo-specific tests.
6. Synthetic data must be generated from documented prompts/models, filtered by deterministic execution where possible, and separated from human-authored examples.
7. Synthetic outputs must not be trained on merely because they parse; execution and functional oracles are required.
8. Preference optimization should be considered only after supervised capability is demonstrated and a safe/unsafe rubric is documented.
9. Retrieval/RAG and tool-assisted coding should be tested as separate configurations. A retrieval layer may improve local repository answers, but it does not cure a weak base model.

### Preferred data order

1. **Python-first:** high-confidence Python functions, tests, tool use, fill-in-the-middle, and repository-context examples from clearly licensed sources.
2. **JavaScript/TypeScript:** add only after Python capability reaches the gate in §8.
3. **C#/.NET only if the product owner confirms it is needed**; do not let the current C# scaffold drive a model decision before licensing and benchmark scope are approved.

## 6. Three-option architecture comparison

| Criterion | From scratch | Pretrained foundation | Dual track |
|---|---|---|---|
| Initial cost | High for a useful model; false economy at 9M scale | Low-medium: reuse weights; spend shifts to inference and adaptation | Medium: support two runtimes and one product adapter layer |
| Compute requirements | Very high for a competitive coder | Moderate for LoRA; hosted/API option for large models | Highest if both models are served simultaneously; manage by one resident engine at a time |
| Time to useful capability | Longest; no current capability evidence | Shortest; credible models already exist | Short for Taksh Code; research line can proceed independently |
| Product differentiation | Highest if a sovereign model eventually works | Lowest by itself; differentiation moves to data, retrieval, tools, evaluation and UX | Best balance: product usefulness plus research independence |
| Licensing complexity | Lowest for weights, but training data still unresolved | License-specific; Apache-2.0/MIT are cleanest | Two provenance chains must be maintained |
| Training-data requirements | Largest; no shortcut | Fine-tuning data can be much smaller, but must still be licensed and decontaminated | Research data remains separate from product data |
| Long-term independence | Highest | Lowest; provider/foundation lock-in risk | Managed if the provider abstraction stays replaceable |
| Engineering risk | Highest: compute, data, optimization and capability risks | Lowest for time to product; highest for dependency/license changes | Medium: integration complexity but failure isolation |

### Why not pure from-scratch now?

The repository has spent substantial effort proving that a small from-scratch model does not generalize. AD-1 and C3 show that the core problem is not a post-processing defect; the model does not generate correct semantics across a broader task mix. A credible from-scratch path would require a resolved corpus, an S4-or-better checkpoint, and an approved training budget — none of which exists.

### Why not pure pretrained adoption?

A hosted or pretrained model can be a useful Taksh Code engine without validating the from-scratch research claim. Treating a foundation as Taksh itself would mix product, research, license and evaluation responsibilities and make the product fragile when the provider or checkpoint changes.

### Why dual track?

Dual track gives Taksh the fastest route to a practical coding surface while preserving the research program that makes the project distinctive. The foundation must remain replaceable, and Taksh Research must not be silently promoted as product capability.

## 7. Recommended Taksh architecture

Separate the product into replaceable layers:

```text
Application / QuantsMind Engineering Studio
  |
  v
Taksh Product API
  |-- model capabilities and policy
  |-- language/context selection
  |-- safety and abuse controls
  |-- provenance and version metadata
  v
Taksh Serving / Provider Abstraction
  |-- LocalInferenceProvider
        (from-scratch S2 / small GGUF)
  |-- HostedCoderProvider
        (Qwen3-Coder or other approved coding API)
  |-- AdapterLoaderProvider
        (approved Taksh Code adapter/model checkpoint)
  v
Taksh Evaluation
  |-- frozen AD-1/C1/C2 regression suites
  |-- broader held-out executable benchmark
  |-- HumanEval/MBPP only after decontamination review
  v
Taksh Model Registry
  |-- foundation model identity and revision
  |-- license and weight provenance
  |-- adapter/checkpoint hashes
  |-- tokenizer and runtime version
```

### Reuse decision

Reuse:
- Frozen evaluation suites, SHA/digest checks and run manifests.
- Existing FastAPI/OpenAI-compatible proof-of-concept patterns, after security review.
- Binding-repair **only as an optional, observable post-processor**, not as a correctness guarantee.
- Existing training/evaluation artifact conventions where compatible with the foundation’s tokenizer and runtime.

Replace or bridge:
- The serving layer needs a provider abstraction; the current Taksh serving path is a from-scratch prototype, not a foundation-model adapter.
- No GGUF/llama.cpp provider exists in the repo. Any local GGUF path requires new, separately authorized runtime code.
- The current tokenizer cannot be reused across a pretrained foundation.

### External dependency policy

Do not make QuantsMind Engineering Studio dependent exclusively on Taksh. The studio should call the Taksh product API, and the product API should be able to switch provider/model without changing the studio’s core workflows.

## 8. Qualification gates

These are **release gates**, not implied results. Current Taksh evidence does not pass them.

| Capability | Minimum gate for experimental Taksh Code alpha | Rationale |
|---|---:|---|
| Syntax validity | ≥0.95 on held-out prompts | A coder that emits broken code cannot be a product alpha. |
| Exact correctness | ≥0.25 on a frozen held-out set of at least 100 cases | Narrow templates can produce a misleading high score; 25% exact is a modest but meaningful floor for a useful alpha. |
| Functional correctness | ≥0.30 on isolated executable cases | Exact AST alone can over-credit near-misses; static and executed results must be reported separately. |
| Parameter binding | ≥0.90 of syntactically valid outputs | Signatures must be honored; binding repair may be used but cannot be the sole means of passing. |
| Multi-file/repository tasks | ≥0.15 successful isolated tasks | Prevents a single-function benchmark from standing in for engineering work. |
| Debugging/repair | ≥0.25 on controlled mutation suites | Coding products are expected to fix their own errors. |
| JavaScript/TypeScript | Same syntax/functional floors after a separate JS/TS benchmark is frozen | Do not transfer Python scores to another language. |
| Latency | p95 ≤10 s for a 1–2K-token task on the selected deployment path | A 30–60 s generation loop is not a practical coding assistant. |
| Safety/reliability | 0 unauthorized executions of generated code; 100% provenance fields present | Executable safety and auditability are hard requirements. |
| Regression | No reduction worse than 0.03 in Python exact/functional versus prior release | Stability is more important than one-off gains at this stage. |

Tool-assisted results must be reported separately from raw model results. Retrieval, compiler feedback, or test-driven repair must never be blended into the model-capability number.

## 10. Risk register

| Risk | Impact | Mitigation |
|---|---|---|
| Foundation license prohibits or constrains commercial redistribution | Product block | Legal review before any weight redistribution; prefer Apache-2.0/MIT and retain use-based restrictions for custom licenses. |
| Training data contaminates held-out evaluation | Invalid capability claims | Freeze and decontaminate before evaluation; keep corpus provenance and evaluation isolation. |
| GGUF runtime is memory-constrained on current hardware | Local mode is unusable | Hosted inference as default; local mode only after a GPU upgrade or a small-model-only decision. |
| Binding repair hides semantic errors | False confidence | Keep it optional and observable; never use it as evidence of intended semantics. |
| Provider model changes without local notice | Behavior drift and evaluation drift | Pin model revision and record inference endpoint/model ID in every run. |
| Hosted code privacy | User code may enter a third-party service | Document provider data policy; self-host by default for sensitive code. |
| Broad coding benchmark is too easy | Over-optimistic gates | Multi-file tasks, debugging, repository editing and held-out tests are separate metrics. |
| From-scratch research consumes budget without product payoff | Dual track becomes unfocused | Research improvements must be measured against AD-1/C3; no product claim unless gates pass. |

## 11. Decisions requiring owner approval

1. **Identity** — Will Taksh Code be a fine-tuned foundation, a provider-backed service, or both?
2. **Foundation license** — Apache-2.0/MIT preferred; OpenRAIL-M/DeepSeek permitted only if legal accepts propagating restrictions and jurisdiction terms.
3. **Local vs hosted** — Approve a GPU upgrade, a hosted API, or a small-model-only local product.
4. **Data policy** — Approve licensed sources, decontamination, retention and redistribution before any corpus acquisition.
5. **Release identity** — Reconcile D1 product versioning with the master roadmap’s v2.5.0 C# slot.
6. **Weight redistribution** — No Taksh adapter or foundation checkpoint may be published until the model-weight license decision is recorded.
7. **Execution policy** — Generated code may only be executed in an approved sandbox; model output alone is never semantically certified.
8. **Studio dependency** — QuantsMind Engineering Studio must not depend exclusively on Taksh until v3.0 production qualification passes.
