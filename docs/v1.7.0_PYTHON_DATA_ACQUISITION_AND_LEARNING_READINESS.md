## 4. Candidate-source methodology

Candidates are **research records**, never approvals. Each entry records the
source identity, evidence references, licence/commercial/provenance gaps,
contamination concerns, expected relevance and volume, the human decisions
required, and an evidence class:

- `VERIFIED_LOCAL_EVIDENCE` — read from artifacts in this repository;
- `REQUIRES_EXTERNAL_VERIFICATION` — confirmable only by inspecting the
  upstream source, which this milestone did not do (no network access was
  used, and no dataset was downloaded);
- `UNKNOWN` — no evidence, and none invented.

Ranking is transparent: nine criteria are summed (authorization feasibility,
provenance quality, Python relevance, data quality, contamination risk,
licensing uncertainty, acquisition cost, processing cost, learning value), and
**authorization feasibility is a hard gate** — a candidate whose authorization
is not feasible never ranks above one whose authorization is feasible,
regardless of its other merits.

## 6. Authorization readiness

`data/python_v1/preflight.py` adds a read-only training-authorization
preflight. It evaluates ten things — candidate identity, source manifest,
immutable revision, human approval evidence, permitted training use,
commercial-use scope, attribution requirements, provenance integrity,
contamination status, approved-source registry consistency — and returns a
structured decision:

```
TRAINING_AUTHORIZED | TRAINING_NOT_AUTHORIZED
```

with stable blocker codes (`source_manifest_missing`,
`authorization_state_is_pending_review`, `authorization_revoked`,
`authorization_expired`, `revision_mismatch`, `use_out_of_approved_scope`,
`commercial_use_not_assessed`, `attribution_obligations_not_assessed`,
`provenance_not_established`, `contamination_status_unknown`,
`source_not_in_approved_registry`, `reviewer_missing`,
`immutable_revision_missing`, `candidate_identity_missing`).

The preflight has **no bypass flag and no unsafe default**, never mutates a
manifest, and never approves anything. Revoked and expired approvals stay
ineligible, and a changed source revision requires renewed authorization.

**Zero-source readiness** (readiness command): declared 0, approved 0,
eligible training sources 0, blocked candidates 0, missing decisions D1–D6,
`production training authorized: False`, default decision `deny`.

## 8. Corrected evaluation and the generation-budget study

The v1.6.0 baseline found 8/8 completions hitting the 64-token budget, which
suggested the measurement was budget-limited. v1.7.0 tested that directly,
inference only, on the M7 checkpoint (sha `6f05cd3d…`), tokenizer sha
`90fd1c8b…`, greedy, seed 1234, Track A cases only (tracks B and C remain
refused: no instruction-qualified checkpoint exists):

| Generation budget | Syntax-valid | Complete program | Termination | Quality | Mean latency |
| --- | --- | --- | --- | --- | --- |
| 32 tokens | 1/8 (0.125) | 1/8 | 8/8 budget | 5 degenerate, 3 invalid | 1.37 s |
| 64 tokens | 1/8 (0.125) | 1/8 | 8/8 budget | 8 degenerate | 3.54 s |
| 128 tokens | 1/8 (0.125) | 1/8 | 8/8 budget | 8 degenerate | 4.24 s |
| 256 tokens | not completed | — | — | — | — |

The 256-token row is a documented **reduced matrix**: the run exceeded the
120-second per-subprocess budget and was not repeated with a larger budget.

**Finding.** Increasing the budget does not change the result: 1/8 at every
budget. The v1.6.0 hypothesis that truncation hid capability is **refuted for
syntax validity**; the actual failure is that the model fills the budget with
degenerate repetition (maximum repeated run of 7+ tokens, mean repeated-bigram
ratio 0.26–0.37, all eight completions classified `degenerate_repetition` at
64 tokens and above). The single "valid" completion is a repetition that
happens to parse.

## 9. Repetition diagnostics

`evaluation/python_eval/budget.py` measures repetition with several
transparent indicators — unique-token ratio, maximum repeated run, repeated
bigram ratio, repeated-line ratio — and classifies each completion as
`complete_program`, `parseable`, `degenerate_repetition` or `invalid`. The
thresholds (repeated run ≥ 8, repeated-bigram ratio ≥ 0.5, repeated-line
ratio ≥ 0.5) are documented engineering defaults, not proofs of failure, and
a repetition that parses is never counted as useful capability.

## 10. Model and compute feasibility

Measured locally: 8 logical cores, 3.91 GiB RAM, 189.8 GiB free disk, Python
3.14.7, torch 2.13.0+cpu, 4 torch threads, **no accelerator**; the processor
is reported as a hash so no machine identity is disclosed.

S2 training memory model (float32 weights, two AdamW moments, batch 1,
context 512): weights 0.035 GiB, optimizer 0.070 GiB, activations 0.004 GiB,
**total 0.109 GiB**. Inference throughput measured in the budget study:
roughly 35–40 tokens/s per case including the forward pass.

Verdict: **`S2_DIAGNOSTIC_FEASIBLE`** for a first authorised run on this
host, with the caveat that 3.91 GiB of RAM is the binding constraint for
anything larger, and that a 100M-token run at this measured rate is on the
order of a week of wall clock — far beyond a local diagnostic budget. A
short diagnostic run (a few million tokens) is realistic; a corpus-scale run
is not, on this machine.

## 11. First authorized learning experiment (design only)

`training/experiment_plan.py` produces the plan. Its status is
**`NOT_AUTHORIZED_FOR_EXECUTION`**.

**Hypothesis.** Training an S2-compatible Taksh checkpoint on a
provenance-verified, owner-approved Python corpus improves held-out Python
completion quality under identical evaluation conditions: same cases, same
surface, same generation settings, same tokenizer and model geometry.

**Prerequisites (13, with status).** Approved source allowlist, verified
licensing evidence, immutable revisions, completed provenance checks,
completed contamination checks, frozen splits, compatible tokenizer,
compatible geometry, reproducible training configuration, sufficient
disk/memory, a defined compute budget, a defined evaluation plan, and safe
execution isolation. The last is `missing` on this host, so functional
correctness remains blocked even if a run were authorized.

**Design.** S2 geometry (9,359,104 parameters, vocab 5,822, d_model 256,
8 layers, context 512) with the frozen tokenizer; next-token prediction on
raw Python under the document policy; sequence length 512, micro-batch 1,
accumulation 8 (4,096 effective tokens), AdamW with warmup and cosine decay;
checkpoints and evaluations every 25 steps; seed 20261021; step budget to be
agreed with the owner; source-group splits 80/10/10. The corpus token count
is written as unknown because no corpus exists.

**Success criteria.** Measured against the same checkpoint family and the
frozen suite: training and validation loss, next-token accuracy, syntax-valid
and complete-program rates on Track A, degenerate-repetition rate,
truncation rate at a pre-registered budget, and held-out family quality.
Instruction-following only on an instruction-qualified checkpoint; functional
correctness only when isolation exists.

**Stop conditions.** Validation divergence, a train/validation gap above 0.5
nats, output collapse (over half the completions degenerate), no held-out
improvement, memorisation, contamination detection, resource exhaustion and
checkpoint corruption. A lower training loss alone is never a success signal.
