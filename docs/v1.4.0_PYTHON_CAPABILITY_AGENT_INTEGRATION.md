# Taksh v1.4.0 — Python Coding Capability and QuantsMind-Agent Integration Readiness

**Disposition:** `v1.4.0 ENGINEERING QUALIFIED — MODEL CAPABILITY INSUFFICIENT`

This document reports the v1.4.0 engineering work: a reproducible Python
coding evaluation framework, bounded generation control, a declared
experimental provider profile, an offline agent-contract harness, and the
actual measurements those produce on the checkpoints that exist in this
repository.

> **Three claims kept apart.** *Engineering qualification*: the evaluation,
> generation and integration machinery works and is tested. *Model capability
> qualification*: a trained model demonstrates useful Python coding — **not
> established; the measured syntax-valid rate is 0%**. *Integration-contract
> qualification*: the wire contract an external agent needs is specified and
> exercised — established against the real application, but against a
> simulated client. *Actual external-agent interoperability*:
> `EXTERNAL_AGENT_INTEGRATION_PENDING`, because QuantsMind-Agent lives in
> another repository that was not modified or inspected.

## 1. Architecture

```text
   QuantsMind-Agent / OpenCode / Cline
                   |
        AgentProviderProfile (declaration)
                   |
     SimulatedCodingAgentClient (offline harness)
                   |
        TakshTransport -> FastAPI app (serving/openai_server.py)
                   |
     PythonCodeGenerator (bounds, prompt safety, diagnostics)
                   |
          Taksh S2 + frozen tokenizer
                   |
     evaluation/python_eval (syntax, sandbox, metrics, runner)
```

| Component | File | Role |
| --- | --- | --- |
| Case schema | `evaluation/python_eval/schema.py` | Versioned, language-neutral case contract |
| Syntax validation | `evaluation/python_eval/syntax.py` | Per-language validator registry and dispatch |
| Isolation | `evaluation/python_eval/sandbox.py` | Capability detection and guarded execution |
| Metrics | `evaluation/python_eval/metrics.py` | Rates with denominators; unmeasurable is `null` |
| Runner | `evaluation/python_eval/runner.py` | Case execution, aggregation, reproducibility |
| Cases | `evaluation/python_eval/data/python_capability_v1.json` | 20 authored cases in 8 categories |
| Case authoring | `evaluation/python_eval/author_cases.py` | Reproducible generator for the case file |
| Runner CLI | `evaluation/python_eval/run_capability.py` | `python -m evaluation.python_eval.run_capability` |
| Generation control | `serving/python_codegen.py` | Prompt validation, bounds, diagnostics |
| Provider profile | `serving/agent_profile.py` | What a local deployment actually offers |
| Agent harness | `evaluation/agent_contract/client.py` | Simulated coding-agent client |

The existing serving stack was **extended, not duplicated**: the generation
controller wraps `serving.local_inference.generate_ids`, and the agent harness
drives the existing `serving/openai_server.py` application in-process.

## 2. API contracts

The existing OpenAI-compatible server exposes exactly three endpoints:

| Endpoint | Method | Behaviour |
| --- | --- | --- |
| `/v1/models` | GET | Model discovery, with a `quantsmind` metadata block (context window, checkpoint step, parameter count) |
| `/health` | GET | Load state, model id, prompt contract, context window |
| `/v1/chat/completions` | POST | Non-streaming chat completion; `max_tokens` default 256, ceiling 4096, clamped to the context window |

Request fields accepted: `model`, `messages`, `max_tokens`, `temperature`,
`top_p`, `stop`, `seed`, `presence_penalty`, `frequency_penalty`, `stream`,
`user`. The fields `tools`, `functions`, `tool_choice`, `n`, `logprobs`,
`top_logprobs`, `logit_bias`, `response_format` and `stream_options` are
declared **so the server can reject them with an explicit error** rather
than silently ignore them.

**Not available and not advertised:** plain `/v1/completions`, streaming
responses, tool calling, structured output.

One contract weakness was found and is reported rather than hidden: the
server **echoes any `model` identifier** instead of rejecting an unknown
one. The experimental client therefore performs the model check itself
(`model_not_found`, HTTP 404 semantics) — the guard belongs where the
external agent is configured.

`serving/agent_profile.py` publishes the same facts as a machine-readable
profile (`quantsmind.agent_profile/1`) with `streaming_supported: false`,
`tool_calling_supported: false`, `structured_output_supported: false`, a
context window, a generation budget, recommended timeouts and the known
limitations.

## 3. Evaluation design

Twenty authored cases across the eight required categories: syntax validity
(3), function completion (4), small algorithm (3), string and list
manipulation (2), control flow (2), debugging (2), test generation (2),
format compliance (2). Every case declares a stable id, category, language
identifier, prompt, prompt surface (`code_completion` or
`chat_instruction`), expected contract, deterministic validator, resource
budget, provenance, contamination class and expected execution environment.

The cases are **authored in this repository**. They are not drawn from
HumanEval, MBPP or any other published suite, so no published-suite licence
applies and no published-suite contamination is claimed. The case file is
generated by `evaluation/python_eval/author_cases.py`, so it is reproducible
and reviewable.

**Prompt surfaces are kept distinct.** A base (pretraining) model is served
raw text: the controller never applies the `qm.chat_instruction/2` renderer to
a model that is not qualified on it. A chat-qualified checkpoint would use the
canonical renderer, and only then.

**Metric denominators are always reported.** A rate that could not be
measured is `null` with a reason, never `0`.

## 4. Security and isolation model

Generated Python is never executed inside the evaluator's process, and a
plain subprocess is never described as a sandbox. `sandbox.py`:

* **detects** whether an isolation mechanism is configured — by default there
  is none, so functional execution is **blocked** and the report says so;
* if an operator configures an external isolation command (container
  runtime, jailed interpreter), the program runs **inside that command**,
  with a process timeout, an output-size cap, a scrubbed environment
  (no inherited credentials), a temporary workspace that is removed
  afterwards, and the required guarantees recorded in the report;
* records which guarantees come from the operator and which this process
  cannot provide (network, filesystem and credential isolation).

On this host no isolation mechanism is configured, so **functional execution
is blocked** and the capability results are syntax-only.

| `py-fmt-001..002` | format_compliance | chat | contains `def <name>` | none |

Contamination classification for every case: `authored`. Provenance:
`authored:v1.4.0`, project-internal.

**Thresholds, stated as policy rather than fitted to results.** A capability
claim requires a syntax-valid rate of at least **0.80** and a functional pass
rate of at least **0.50** on the executed subset. The measurement below is
insensitive to those numbers: the observed syntax-valid rate is 0.00, which
fails any plausible bar. No threshold was tuned to make a gate pass.

## 7. Actual capability results

20 cases, 64 new tokens per case, CPU, greedy decoding:

| Model class | Syntax-valid | Contract pass | Functional pass | Mean latency |
| --- | --- | --- | --- | --- |
| untrained S2 | **7/20 (0.350)** | 0/9 (0.000) | not measurable (blocked) | 3.42 s |
| real-data-trained S2 (M7) | **0/20 (0.000)** | 0/11 (0.000) | not measurable (blocked) | 3.57 s |
| synthetic-only S2 (v1.3.0) | **0/20 (0.000)** | 0/11 (0.000) | not measurable (blocked) | 3.61 s |

Breakdown by prompt surface (M7 checkpoint): `chat_instruction` 0/15
syntax-valid, `code_completion` 0/5. Failure categories: 20 ×
`syntax_error`.

Qualitative evidence (verbatim, first case, 64 tokens):

* M7 (real-data-trained): `'def __init__( """ """ if not None, self.get_name(self, "")'`
* v1.3.0 synthetic-only: `'totalcaled =ed =ed + total totalcal""""""""""""""'`
* untrained: `'thatthatthatthatthatthatthatthatthatthatthatthatthatthat'`

**Interpretation, stated plainly.** The trained checkpoints produce
*Python-shaped* fragments that do not parse, and the untrained checkpoint
produces degenerate repetition that occasionally parses. Neither is evidence
of Python proficiency. The scoring surface is part of the explanation: the M7
model is a raw-code base model while the suite is mostly instruction-style,
so the measured rate is a lower bound that mixes a surface mismatch with a
capability question. The honest reading is that **no checkpoint in this
repository demonstrates usable Python coding ability**, and the corrective
action is a data and training intervention, not a change of evaluation
criteria.

## 8. QuantsMind-Agent integration readiness

The offline contract harness (`evaluation/agent_contract/client.py`) drives
the real FastAPI application in-process and covers: model discovery, health,
request serialisation, response parsing, unknown model (client-side refusal),
malformed request (422), non-positive token limit (400), tool request
(explicit 400 refusal), error-code consistency, bounded concurrency, and call
recording.

Status: **`EXTERNAL_AGENT_INTEGRATION_PENDING`**. QuantsMind-Agent is a
separate repository; it was neither modified nor inspected, so no claim of
real interoperability is made. The profile in `serving/agent_profile.py` is
what an agent operator would configure against, and it advertises nothing
the server does not do.

## 9. Known limitations

* **Functional execution is blocked on this host**, so no functional pass
  rate exists; syntax-only results are reported with that limitation.
* **The suite is 20 authored cases**: enough to expose a total failure, not
  enough to characterise a working model. It is a smoke suite, not a
  benchmark.
* **The suite is mostly instruction-style** while the available checkpoints
  are code-completion base models.
* **The client's model list is cached**; a server whose model set changes at
  runtime needs `refresh=True`.
* **No KV cache**: generation re-runs a full forward pass per token, so
  latency is high and long generations are impractical on CPU.
* **Pre-existing defect in the legacy `serving.local_inference.generate()`**
  helper: it tests for a token named `[EOS]`, which the tokenizer does not
  have, so its early-stop check never fires. The shared `generate_ids()` path
  used by the server and by this evaluation is unaffected.
* **Cross-device determinism is not claimed**; only CPU behaviour is measured.
* The evaluation framework is language-neutral, but the *dataset* interface
  is Python-scoped (`quantsmind.python_dataset_manifest/1`, class
  `PythonDataset`): a future language needs a new contract and schema, not
  engine changes.

## 10. Corpus authorization blockers

* **D1–D5 (licensing) remain unresolved.** The shipped v1.2.0 contract
  approves zero sources, so no v1.2.0 corpus exists and no model can be
  trained on one.
* **D3 (allowlist) is not widened** by this version; the real-data-trained
  checkpoint used here predates the v1.2.0 pipeline and its licence evidence
  is the historical one, not a v1.2.0 decision.
* **Contamination coverage is empty**: HumanEval and MBPP have no local copy
  here, so the benchmark registry reports them as not checked.
* **Minimum viable authorised corpus for the next experiment:** at least one
  source with a recorded licence decision, reviewer, rationale, evidence hash
  and pinned revision; a v1.2.0 manifest with `corpus_ready: true`; and a
  held-out split that is not drawn from the evaluation cases.

## 11. Model capacity assessment and recommendation

* **S2 (9,359,104 params, 5,822 embedding rows, ctx 512)** is the only rung
  that matches the frozen tokenizer. Its measured limits are known: 2.85–2.97
  characters per token, 32–43% identifier fragmentation, 57% keyword
  single-token coverage, and a 64-token budget producing unusable output.
* **The S3 geometry (16,257,280 params) is unreachable today.** A
  checkpoint with that geometry exists in `runs/code_pretrain`, but its
  vocabulary (32,768) matches no tokenizer in this repository, so it cannot
  be served with the frozen tokenizer, and its sampled output is degenerate
  (`'_path.path.path.path...'`). That is concrete evidence that the orphan
  vocabulary is a real problem, not a theoretical one.
* **The bottleneck is data and training, not capacity.** A model scoring 0%
  syntax-valid says nothing yet about whether 9M or 30M parameters is the
  limit. Widening the vocabulary now would change the experiment before the
  data exists.
* **Recommendation (not executed).** Settle D1–D5 and D3, build a v1.2.0
  corpus, then run the v1.3.0 trainer on the S2 rung for 300 steps at context
  512 and re-measure this same suite. Estimate: on this CPU-only host about
  1.5–2 hours and ~1.2M tokens; on a single GPU well under an hour. Only if
  S2 still produces invalid code on a real corpus is a vocabulary decision
  (D6) and a larger rung justified.

## 12. v1.5.0 handoff and reproducible commands

```bash
# v1.4.0 qualification suite
python -m pytest tests/test_v140_capability.py -q

# capability evaluation (three model classes, reported separately)
python -m evaluation.python_eval.run_capability --untrained \
    --model-id qm-code-m3-9m --class untrained --max-new-tokens 64 \
    --out reports/untrained.json
python -m evaluation.python_eval.run_capability \
    --checkpoint runs/m7_pretrain/checkpoint_last.pt \
    --tokenizer tokenizer/qm_code_bpe_v0.json --model-id qm-code-m3-9m \
    --class real-data-trained --max-new-tokens 64 --out reports/m7.json

# regenerate the case file
python -m evaluation.python_eval.author_cases

# regressions
python -m pytest tests/test_v130_pretraining.py tests/test_v120_python_data.py \
    tests/test_v120_tokenizer_analysis.py -q
python -m pytest tests/test_v110_contract.py tests/test_token_contract_and_chat.py \
    tests/test_training_correctness.py tests/test_code_serving.py -q
```

**Handoff to v1.5.0.** The v1.5.0 instruction-tuning milestone needs (a) a
model that can at least produce parseable Python, which no checkpoint in this
repository currently does, (b) an authorised corpus, (c) a decision on
whether the instruction format reuses `qm.chat_instruction/2` for a base model
that was never trained on it, and (d) a capability suite large enough to
distinguish a working model from a degenerate one. None of these is
engineering work this version could complete; the honest next step is the
corpus decision, not more evaluation code.
