# Taksh v1.2.0 — Python Data and Tokenizer Foundation

**Status:** pipeline implemented and qualified on synthetic fixtures.
**Version disposition:** `v1.2.0 QUALIFIED — PIPELINE SCOPE` and, separately,
`CORPUS NOT YET APPROVED`.

This document describes the data foundation built in v1.2.0. It is a
technical reference, not a competing roadmap: the authoritative plan remains
`docs/roadmap/TAKSH_MASTER_DEVELOPMENT_ROADMAP.md` §3.

> **Scope boundary.** Every number below comes from synthetic fixtures or from
> bounded measurements on data already inside this repository. No dataset was
> downloaded, no corpus was built from an unapproved source, and no model was
> trained. Qualifying the pipeline is not the same as approving a corpus:
> the shipped contract approves **zero** sources, so a real run produces
> nothing until the owner approves sources and decides D1–D5.

## 1. Architecture overview

The pipeline is a sequence of independent, deterministic, bounded stages:

```text
approved source registry (data/contracts/python_v1.yaml)
        v
licence + provenance gate          registry.py
        v
local ingestion (read-only)        ingest.py
        v
normalisation + quality filtering  quality.py
        v
exact / near duplicate detection    dedup.py
        v
benchmark contamination screening  benchmarks.py
        v
source-group aware splitting       splits.py
        v
deterministic manifest + card      manifest.py
        v
validated training interface        interface.py
```

Module layout (`data/python_v1/`):

| Module | Responsibility |
| --- | --- |
| `registry.py` | Default-deny source registry, licence evidence verification, pinned revisions, contract fingerprints |
| `ingest.py` | Bounded, read-only, symlink/junction-safe traversal and decoding |
| `quality.py` | Lossless normalisation, AST validation, quality rules, secret detection |
| `dedup.py` | Exact hashing, code-token shingles, MinHash/LSH near-duplicate groups |
| `splits.py` | Component assignment, leakage audit, readiness assessment |
| `benchmarks.py` | Versioned benchmark registry and contamination screening |
| `manifest.py` | Deterministic manifest, artifact checksums, data card |
| `interface.py` | Validated reader for the v1.3.0 training pipeline |
| `pipeline.py` | Orchestration and the `python -m data.python_v1` command |

Reuse of existing repository components was preferred over new code:
`data.licence_paths.path_within` for subtree containment,
`data.contamination_audit.normalise_for_match` for benchmark normalisation,
`data.filters.word_shingles` for n-gram screening,
`training.checkpoint_schema.code_revision` for provenance, and
`training.tokenizer_contract` for tokenizer identity and contract detection.

## 2. Source registry design

A source is a structured entry in the versioned contract. Required fields:

| Field | Meaning |
| --- | --- |
| `id` | Stable identifier, `[a-z0-9][a-z0-9._-]*` |
| `kind` | `local_directory` (the only permitted kind) |
| `location` | Path relative to the contract file; a URL is rejected |
| `revision` | Pinned content identity `sha256:<64 hex>` |
| `license.spdx` | Declared licence |
| `license.decision` | `approved` \| `rejected` \| `unresolved` — an owner decision |
| `license.evidence` | Licence file inside the source |
| `license.evidence_sha256` | Hash of that file |
| `approval.status` | `approved` \| `pending` \| `rejected` |
| `approval.reviewer`, `approval.rationale` | Who decided, and why |

Optional: `project`, `attribution`, `allowed_extensions`, `excluded_paths`,
`prune_dirs`, `notes`.

Enforcement rules (each with a stable reason code):

* Unknown sources are denied — they are not in the contract at all.
* `policy.default_decision` must be `deny`; the loader raises `ContractError`
  otherwise, so the allowlist cannot be widened by editing one line.
* A source with a licence decision other than `approved` is denied
  (`license_decision_unresolved`), even if its licence file exists and hashes
  correctly. A top-level licence file is evidence, not a decision.
* A licence outside `policy.allowed_spdx` is denied (`license_not_allowlisted`).
* A missing owner approval is denied (`approval_not_granted`).
* Missing, out-of-tree or mismatched licence evidence is denied
  (`license_evidence_missing`, `license_evidence_outside_source`,
  `license_evidence_hash_mismatch`).
* An unpinned or missing revision is denied (`revision_not_pinned`,
  `revision_missing`); a revision that does not match the observed snapshot is
  denied after ingestion (`revision_mismatch`).
* Unknown keys in a source, licence or approval block are rejected, so a typo
  cannot silently disable a control.

The pinned revision is the SHA-256 of the eligible Python file set of the
source (path plus content hash, sorted), which is exactly the set the build
consumes. Two builds of the same snapshot therefore produce the same corpus.

## 3. License and provenance controls

The registry implements **policy enforcement only**. It does not determine
whether a licence permits a particular use, and it does not resolve the
roadmap's D1–D5 licensing questions. Those remain owner decisions and are
reported as unresolved.

Every record that enters the corpus carries `source_id`, `source_revision`,
`license_spdx`, `attribution` and `project`, so a record can be traced back to
an approved source, a pinned revision and a recorded licence decision. The
manifest repeats the same information per source, plus the observed snapshot
revision, so a reviewer can compare what was declared with what was found.

## 4. Ingestion and normalisation

Ingestion is read-only and bounded. The traversal never writes to the source
tree and never follows a link.

| Control | Behaviour |
| --- | --- |
| Containment | Every candidate path is re-resolved and compared with the resolved source root; a path outside it is refused (`path_escape_refused`) |
| Links | Symbolic links and Windows junctions are skipped, never traversed (`link_skipped`) |
| Order | Directory entries are sorted, so two runs produce the same candidate list in the same order |
| Path safety | Relative POSIX paths only; `..` and absolute paths cannot be produced |
| Limits | `max_files`, `max_file_bytes`, `max_total_bytes`, `max_path_depth`; reaching one marks the run `truncated` with a reason, never a silent smaller corpus |
| Directories | `.git`, `__pycache__`, `.venv`, `venv`, `node_modules`, `.mypy_cache` are pruned; contract `excluded_paths` exclude whole subtrees |
| Extensions | Only the extensions the source declares (`.py` by default) |
| Reading | Read-only binary reads; file size re-checked after read |

Encoding rules are explicit. The declared encoding is detected with
`tokenize.detect_encoding`, which honours a UTF-8 BOM and a PEP 263 coding
cookie. A file that does not decode is rejected with `encoding_error` unless
the contract lists explicit fallbacks, in which case the fallback is used and
counted in `filtering.encoding_fallbacks`. NUL bytes and a high share of
control characters mark a file as `binary_content`. Diagnostics carry counts
and paths only — never file content.

Normalisation is deliberately minimal, because a Python corpus is a *code*
corpus:

| Transformation | Lossless? | Note |
| --- | --- | --- |
| CRLF → LF, lone CR → LF | Yes | Python treats all three as line boundaries; mixed endings break reproducibility across platforms |
| Leading UTF-8 BOM removed | Yes | The BOM is not part of the program text |
| Everything else | Untouched | Comments, docstrings, blank lines, trailing whitespace inside string literals, identifier names and indentation are preserved byte-for-byte |

NFKC normalisation is deliberately **not** applied: it rewrites identifiers
and string contents, which changes program semantics.

## 5. Quality filtering

Quality rules run in a fixed order, and the first failure wins, so the
recorded reason is stable for a given input and configuration.

| Reason code | Trigger |
| --- | --- |
| `empty_file` | No non-whitespace content |
| `too_small` / `too_large` | Byte size outside the configured range |
| `unsafe_metadata` | Control characters or bidirectional overrides |
| `generated_code` | Configured marker in the file header (for example `@generated`) |
| `vendored_dependency` | Path matches a configured vendored/generated path pattern |
| `minified_artifact` | Longest line above the threshold and average line length above the threshold |
| `excessive_repetition` | Compression ratio below the configured floor (highly repetitive content) |
| `embedded_secret` | A credential pattern matched |
| `reserved_token_literal` | The text contains a reserved spelling (`<eos>`, `<\|user\|>`, …) that would be encoded as a reserved id |
| `syntax_error` / `too_complex` | The file does not parse as Python |
| `trivial_sample` | No executable statements (a docstring-only module) |
| `low_information` | Distinct-token ratio below the configured floor |
| `too_few_lines` | Fewer lines than configured |

Comments and docstrings are **not** removed: for Python they carry a large
part of the training signal, and deleting them is a semantic change.

Secret detection reports the *kind* of credential only (`private_key`,
`aws_access_key`, `github_token`, `slack_token`, `jwt`,
`credential_assignment`). The matched text is never copied into a log, a
manifest, a diagnostic or the data card; the file is excluded and only the
count is kept.

Thresholds are configuration, not constants, and they are engineering
defaults. They are not claimed to be empirically optimal, because no sweep was
run.

## 6. Deduplication

**Exact duplicates.** The SHA-256 of the normalised text identifies identical
samples. Members are grouped, one representative is chosen deterministically
(the smallest `source_id/file_path` pair), and the rest are removed. The group
is retained so a split can never separate copies.

**Near duplicates.** Source code is not prose, so similarity uses a *code
token* stream (names, numbers, strings, operators, comments) rather than
words. Shingles of `k = 8` consecutive code tokens are hashed with BLAKE2b,
MinHash signatures are computed with fixed permutations, and candidates are
retrieved with LSH banding — never with an all-pairs comparison. Every
candidate is then verified with an exact Jaccard computation, so a banding
collision cannot create a false positive.

Boilerplate is handled explicitly: a shingle that occurs in more than
`boilerplate_df_ratio` of the samples *and* in more than one sample is
removed from the comparison, so a shared licence header cannot make two
different files look similar.

Bounded behaviour: `max_shingles_per_record` caps the shingles per sample,
`max_bucket_candidates` caps the comparisons per band bucket, and both caps
are recorded in the statistics when reached. Results are reproducible: the
same input produces the same groups, representatives and statistics.

## 7. Split integrity

The unit of assignment is a **component**: the connected component of the
graph whose nodes are samples and whose edges are (a) a shared source group
and (b) a shared exact or near-duplicate group. Assigning whole components
satisfies both integrity properties at once:

* no source group straddles train/val/test;
* no known duplicate, exact or near, is separated across splits.

Assignment is deterministic. Components are ordered by a stable hash of their
identity and filled by the largest-remainder method, so the result depends
only on the component set and the configured proportions — not on input
order, dictionary ordering or run count. Proportions are configuration
(`splits.proportions`), and the seed is recorded in the manifest.

Readiness is explicit. A split is reported `ready: false` with the reason
(`val: 0 groups < 1 required`) when the corpus is too small to support the
requested proportions. No statistical claim is made from a small holdout, and
a not-ready split is refused by the training interface unless the caller
explicitly asks for it.

The manifest records the per-component assignment, the per-split counts, the
component counts and the integrity audit (sources straddling splits, duplicate
digests straddling splits, components straddling splits).

## 8. Contamination controls

`data/contracts/benchmarks_v1.yaml` is a versioned registry of benchmark
families. Each entry declares an `id`, a `version`, an `availability`
(`available` or `unavailable`), a local `path` and the text `fields` to
screen.

* Nothing is downloaded. Registering HumanEval or MBPP means placing an
  approved local copy and pointing the entry at it.
* An entry marked `unavailable`, or one whose local file is missing or
  unreadable, is reported as **not checked**. The verdict is then
  `unavailable`, never `clean`.
* Screening is lexical, in three arms: exact match on the SHA-256 of the
  NFKC/lowercased/whitespace-collapsed text, shared 13-word shingles, and an
  optional MinHash near-match arm. Paraphrases, renamed identifiers and
  re-implementations are not detected, and the report says so.
* A contaminated sample is removed **before** splitting, so it can never be
  assigned to a holdout.
* The shipped registry marks HumanEval, MBPP and the hand-transcribed
  in-repo subset as `unavailable`, so a clean verdict over them is never
  claimed. The in-repo transcribed subsets are screened separately by the
  existing `data.contamination_audit` module.

A clean result is therefore only ever a statement about the suites that were
available and checked, and the manifest records exactly that, per suite.

## 9. Manifest specification

`quantsmind.python_dataset_manifest/1`, written as `manifest.json` beside the
shards, with a `DATA_CARD.md` generated from it. Contents:

| Group | Fields |
| --- | --- |
| `pipeline` | `version`, `code_revision`, `contract_fingerprint`, `registry_fingerprint` |
| `sources` | per-source decisions (approval, licence, reasons), `approved`/`denied` lists, observed revisions |
| `configuration` | normalisation, quality, dedup, limits, encoding, policy (the exact configuration used) |
| `filtering` | seen, kept, rejected total, per-reason rejects, ingest diagnostics, encoding fallbacks, truncation state |
| `deduplication` | exact and near duplicate counts, groups, components, boilerplate removals, bounded-behaviour flags |
| `splits` | proportions, seed, counts, component counts, readiness, insufficiency reasons, integrity audit, per-component assignment |
| `contamination` | verdict, hit count, coverage (checked / not checked suites), method, limitations, sample hits |
| `tokenizer` | path, SHA-256, vocabulary size, prompt contract id |
| `artifacts` | per shard: name, SHA-256, byte size, record count |
| `notes` | `corpus_class` (`production`/`synthetic`), `synthetic` flag, `corpus_ready` flag and its explanation |
| `manifest_sha256` | SHA-256 of the canonical manifest, excluding the field itself |

Two deliberate properties:

* **No timestamps, no absolute paths.** Two builds of the same inputs produce
  byte-identical manifests and byte-identical shards. The verification suite
  asserts exactly that.
* **The manifest describes reality.** Checksums are computed from the written
  files and the counts are read back from those files.

## 10. Training interface

`data/python_v1/interface.py` is the boundary between preparation and the
v1.3.0 training pipeline. `PythonDataset(manifest_path, split, ...)` refuses
to hand out samples unless:

* the manifest exists and has the expected schema;
* the requested split exists as an artifact;
* the artifact's SHA-256 and byte size match the manifest;
* the split is `ready` (unless the caller passes `require_ready=False`
  explicitly, which is recorded as a deliberate override);
* every record's `content_sha256` matches its text, and the record schema
  matches;
* when a tokenizer path is supplied, its file hash equals the one recorded in
  the manifest, and the tokenizer serves the prompt contract the corpus was
  prepared under.

There is no silent fallback to an unapproved dataset, and no path that lets a
model train on a corpus prepared with a different tokenizer. The interface
consumes prepared records; it does not change v1.3.0 training behaviour.

## 11. Tokenizer analysis

Measured with `training/tokenizer_analysis.py` on two permitted local
samples. No external tokenizer or model was downloaded, so this is a
self-measurement, not a competitive benchmark.

**Sample A — this repository's own Python source** (150 files, 1,295,241
characters, 435,478 tokens). **Sample B — the existing local code corpus**
`data/code_corpus_v1.jsonl` (88 files, 1,503,751 characters, 528,186 tokens).

| Metric | Sample A | Sample B | Reading |
| --- | --- | --- | --- |
| Characters per token | 2.97 | 2.85 | Against the byte-level baseline of 1.0 byte/token, a 2.9× compression factor |
| Bytes per token | 2.97 | 2.85 | Same measure, byte-exact |
| Tokens per character | 0.336 | 0.351 | — |
| Tokens per lexical token | 2.32 | — | A lexical token (name, number, string, operator) costs ~2.3 model tokens |
| Identifier fragmentation | 32.1% | 43.2% | Share of identifiers costing more than one token |
| Mean tokens per identifier | 1.91 | — | — |
| Keywords in one token | 57.1% | 57.1% | 24 of 35 Python keywords |
| Operators in one token | 54.2% | 54.2% | — |
| Tokens per string character | 0.386 | — | String literals are the densest area |
| Tokens per newline | 0.0044 | — | Newlines are nearly free |
| Tokens per indented line (indent only) | 1.14 | — | Four-space indents cost ~1 token |
| Tokens per Unicode character | 5.85 | — | Non-ASCII text is expensive |
| Unknown-token rate | 3.0e-05 | 0.0 | Effectively zero; the ByteLevel alphabet is complete |
| Lossless round-trip failures | 0 / 150 (0%) | 0 / 88 (0%) | Decode with `skip_special_tokens=False`: the artifact reproduces the text exactly |
| Policy round-trip failures | 22 / 150 (14.7%) | 0 / 88 (0%) | Library default `decode()` skips special tokens; see below |
| Files containing reserved spellings | 27 (141 occurrences) | 0 | Injection exposure, not artifact loss |
| Bytes covered by a 4096-token window | 12,183 | — | ~12 KB of Python per context window |

**Round-trip: root cause.** The 22 policy failures are **not a tokenizer
defect**. Three facts, each measured:

1. `tokenizers` 0.23.1 registers `<pad>`, `<bos>`, `<eos>`, `<unk>` (and, in
   the v1.1.0 derivation, `<|system|>`, `<|user|>`, `<|assistant|>`,
   `<|end_of_turn|>`, `<|tool|>`, `<|fim|>`) as `AddedToken(special=True)`.
2. `Tokenizer.decode(ids)` defaults to `skip_special_tokens=True`, so a
   registered special token is removed from the decoded text.
3. A *literal spelling* of a reserved token in ordinary source text is
   encoded to that reserved id — for example `tokenizer.token_to_id("<eos>")`
   encodes `<eos>` to id 2 — so the default decode silently deletes it.

With `decode(ids, skip_special_tokens=False)` the text is reproduced
**byte-exactly** in every measured case: lossless failures are 0 of 150 and
0 of 88, and the classifier reports `genuine_loss: 0` with all 22 policy
failures attributed to `special_token_drop`. The tokenizer has no
post-processor, so the encoder inserts nothing on its own. The behaviour is
therefore an **expected special-token decoding policy** of the library, not
an artifact defect, and no retraining, vocabulary change or checkpoint change
is warranted.

**What the behaviour does mean for the corpus.** A reserved spelling in
ordinary text becomes a reserved id in the token stream. Under the v1.1.0
control contract the control-range ids are role markers, so such a file
would forge a role boundary in the `qm.chat_instruction/2` renderer — a
**data-plane injection risk**, not a tokenizer fault. v1.2.0 therefore
excludes such samples with the reason code `reserved_token_literal` rather
than rewriting them, and the exclusion is configuration-driven
(`quality.reserved_literals`). A larger vocabulary would not fix this; it is
a corpus-side control.


**Control-token range (v1.1.0).** The derived control tokenizer (5,828 ids)
was measured against the base tokenizer (5,822 ids) on the same sample:
fertility changed by −1.1e-4 tokens per character, i.e. no regression, as
expected for an appended marker range with no retrained merge. The small
negative delta comes from files that contain control-marker literals, which
the derived tokenizer encodes as one token instead of many.

**Baseline.** The documented comparison baseline is a byte-level fallback at
one token per UTF-8 byte. `bytes_per_token` is therefore the compression
factor against it. No external tokenizer was downloaded or compared.

## 12. Migration decision

**Decision: `TOKENIZER_ACCEPTED_WITH_LIMITATIONS` for the current artifact,
with a measured vocabulary recommendation for the owner's D6 decision.**

The decision rules (documented engineering defaults, not a sweep) evaluate
the **lossless** round-trip rate, the identifier fragmentation and the
fertility. On both local samples the artifact is lossless (0 failures), so
no migration-level defect is present. What remains are limitations:

1. **Fertility is below the acceptance threshold in both samples**
   (2.97 and 2.85 characters per token against a 3.0 acceptance threshold),
   which is what a 5,822-token vocabulary yields on Python.
2. **Identifier fragmentation is high** (32.1% and 43.2%, against a 50%
   migration threshold). Only 57.1% of Python keywords and 54.2% of the common
   operators are single tokens, and string literals cost 0.386 tokens per
   character.
3. **Reserved-literal exposure exists in some corpora** (27 of 150 files in
   this repository, 0 of 88 in the local code corpus). It is handled
   corpus-side by the `reserved_token_literal` rule, not by the tokenizer.

An earlier draft of this report classified the round-trip difference as a
tokenizer defect and recommended migration on that basis. The investigation
in §11 corrected that: the difference is the library's documented
`skip_special_tokens=True` decode policy, the artifact reproduces every
measured file exactly with skipping disabled, and the vocabulary size is a
separate, measured limitation. The corrected verdict is therefore
`TOKENIZER_ACCEPTED_WITH_LIMITATIONS`.

Recommendation to the owner for D6 (the vocabulary decision, which this
version does not take):

| Item | Current | Proposed (owner decision) |
| --- | --- | --- |
| Vocabulary | 5,822 (5,828 with the v1.1.0 control range) | 32,768 (`configs/model/code_30m.yaml` already declares this size) |
| Embedding rows | 5,822 × 256 = 1,490,432 params | 32,768 × 256 = 8,388,608 params (+6,898,176) |
| S2 rung total | 9,359,104 params | ≈ 16,257,280 params at the same depth |
| Training data | — | The v1.2.0 train split only; holdouts and benchmark-screened content must not contribute merges |
| Control range | ids 5822–5827 | Preserved with the same ids, so the prompt contract does not change |
| Checkpoint compatibility | — | Existing v1.0.0/v1.1.0 checkpoints embed the 5,822-row table and cannot be loaded into a resized model; they stay servable through the legacy tokenizer artifact |

Plan if D6 approves a larger vocabulary:

1. Train `qm_code_bpe_v1.json` from the v1.2.0 train split only, with the
   reserved control range preserved.
2. Configure a new model rung with the larger vocabulary; keep the legacy
   rung and the legacy tokenizer loadable.
3. Never delete or silently replace the legacy tokenizer or any existing
   checkpoint.
4. Re-measure with this module and require the lossless round-trip rate to
   stay at 1.0 before the new artifact is used for training.

The roadmap (§23, D6) makes the tokenizer vocabulary an owner decision that
must be fixed before training. v1.2.0 changes no tokenizer artifact, no
vocabulary size and no model configuration; the measurements above are the
input to that decision.

## 14. Known limitations

* **No approved corpus.** The qualification is pipeline qualification on
  synthetic fixtures. It is not evidence that a real licensed Python corpus
  exists, is legal for the intended use, or is ready to train on.
* **D1–D5 remain unresolved.** The registry enforces decisions an owner has
  recorded; it does not make them.
* **Contamination screening is lexical.** Paraphrases, renamed identifiers and
  re-implemented logic are invisible to it. The published HumanEval and MBPP
  suites are not available locally and are reported as not checked.
* **Boilerplate handling is a shingle-frequency heuristic.** It removes
  frequent shingles from the comparison; it does not detect a project whose
  files are all near-duplicates of one another.
* **The split unit is the source group.** With few sources the holdouts are
  coarse, and the pipeline reports that instead of splitting one source
  across splits.
* **The tokenizer's reserved-literal exposure is corpus-dependent.** 27 of
  150 files in this repository contain a reserved spelling; 0 of 88 in the
  local code corpus. The artifact itself is lossless (§11); the exposure is
  a data-plane injection risk, handled corpus-side by
  `reserved_token_literal`.
* **Thresholds are engineering defaults.** No sweep was run, so the decision
  rules are policy rather than optimised constants.
* **Near-duplicate detection is lexical.** It matches token sequences, so a
  re-implementation with new names is not detected.
* **Windows privilege note.** Symbolic-link creation needs a privilege this
  host does not grant; that one test is skipped and reported as such.

## 15. Dependencies for v1.3.0

1. **An owner-approved source set.** A contract with approved sources, pinned
   revisions and licence evidence hashes, so the pipeline has something to
   build from. D3 decides which sources.
2. **A licence decision (D1–D5).** Unresolved licensing blocks inclusion by
   design; the pipeline keeps denying those sources until the decision is
   recorded in the contract.
3. **The published benchmark suites.** Approved local copies of HumanEval and
   MBPP, so the contamination verdict can cover them instead of reporting
   them as not checked.
4. **A tokenizer decision (D6).** The measurements in §11 and §12 are the
   input to the vocabulary decision that must be fixed before training. The
   current artifact is accepted with limitations; the recommendation is
   optional vocabulary growth to 32,768, which keeps the legacy tokenizer and
   every existing checkpoint loadable. Reserved-literal exposure is handled
   corpus-side by the `reserved_token_literal` rule and needs no tokenizer
   change.
5. **A corpus size target.** The roadmap specifies 100M tokens with at least
   60% Python, at least 8% comments/docstrings and at least 5% held-out
   Python. Nothing in this version reaches that; the split readiness check
   and the manifest counts make the shortfall explicit instead of hiding it.
6. **No change to the v1.1.0 contracts.** The prompt contract
   (`qm.chat_instruction/2`), the reserved control range and the
   `quantsmind.checkpoint/2` schema stay as they are; the training interface
   validates against them rather than altering them.
