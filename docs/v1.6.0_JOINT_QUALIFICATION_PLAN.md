# Taksh–QuantsMind-Agent Joint Qualification Plan (read-only)

**Status:** plan only. This milestone did **not** execute a joint
qualification, and no interoperability claim beyond the v1.4.0 IQ-1 result is
made. The QuantsMind-Agent repository was not modified.

## 0. Why a re-qualification is needed

v1.4.0 (IQ-1) verified the transport contract between the real
QuantsMind-Agent provider (`OpenAICompatProvider`) and the Taksh server over
localhost. v1.5.0 changed how a **base** checkpoint is prompted (raw text
instead of the chat template) and v1.5.0/v1.6.0 changed model-id validation
(unknown ids are now refused). The wire contract is unchanged, but the
rendering an agent receives is different, so the earlier evidence is stale for
prompt rendering.

## 1. Preconditions

| Item | Requirement |
| --- | --- |
| Taksh revision | exact commit SHA, recorded in the report |
| Agent revision | exact branch and commit SHA of the concurrently developed repository, recorded before the run |
| Checkpoint | identity plus SHA-256, cross-checked against `/v1/models` |
| Tokenizer | identity plus SHA-256, compatible with the checkpoint |
| Configuration | isolated `QM_CONFIG_DIR`; the user's real configuration is neither created nor modified |
| Credentials | none: a localhost endpoint is treated as unauthenticated |
| Network | loopback only; no cloud service and no paid API |
| Authority | written authorization for the joint run, including permission to read the agent repository |

## 2. Test matrix (to execute under separate authorization)

| ID | Check | Expectation |
| --- | --- | --- |
| JQ-1 | Exact version identification of both repositories | recorded, no drift |
| JQ-2 | Server startup and model discovery | `/health` 200, `/v1/models` lists the loaded id |
| JQ-3 | Chat completion through the agent provider | 200 with a valid `chat.completion` body |
| JQ-4 | Base-checkpoint prompt handling | the served prompt is raw text, not a chat template |
| JQ-5 | Unknown model identifier | refused with a structured error, not echoed |
| JQ-6 | Token-limit enforcement | `usage.completion_tokens` respects the request |
| JQ-7 | Malformed request | a typed agent error, no crash |
| JQ-8 | Server unavailable | a typed `NetworkError`, no crash |
| JQ-9 | Shutdown and recovery | controlled error, then successful recovery |
| JQ-10 | Capability declarations | tool calling, streaming and structured output declared unsupported and refused |
| JQ-11 | Agent workflow observability | prompt, finish reason, token counts and error codes visible to the agent |
| JQ-12 | Generated-code quality | the same completion-track suite used in v1.6.0, with the same budget, so the two results are comparable |

## 3. Constraints

* No change to the agent's source, default provider, credentials, production
  configuration or release packaging.
* No write into the agent repository; the run reads it.
* No external provider is contacted, and no default provider is replaced.
* Every step is bounded: one request per case, a fixed token budget, a
  controlled startup and shutdown.
* Results are recorded verbatim; no sample is rewritten or trimmed.

## 4. Exit criteria

The joint qualification is complete when JQ-1…JQ-12 have recorded outcomes,
the agent repository is demonstrably unchanged, and the report states plainly
which conclusions are about *transport* and which are about *capability* —
the two must not be merged.
