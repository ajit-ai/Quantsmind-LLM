# Taksh v1.3.0 — Python-Focused Pretraining

**Status:** engineering-qualified on a synthetic fixture corpus.
**Disposition:** `v1.3.0 ENGINEERING QUALIFIED — CORPUS NOT YET APPROVED`.

This document is the technical reference for the v1.3.0 training system. It
is not a competing roadmap: `docs/roadmap/TAKSH_MASTER_DEVELOPMENT_ROADMAP.md`
§4 remains authoritative. Where the roadmap and the implementation scope
disagree, the disagreement is recorded explicitly in §2 and §14.

> **Three different claims.** *Engineering qualification* means the training
> system works correctly under controlled conditions. *Corpus readiness* means
> a legally approved, sufficiently large Python corpus exists. *Model
> capability* means a trained model demonstrates useful Python ability on
> independent evaluations. This version establishes the first only. The
> shipped v1.2.0 contract approves zero sources, so the second does not hold,
> and no capability claim of any kind is made.

## 1. Architecture

```text
v1.2.0 dataset manifest
        v
training/authorization.py     mode, licence, revision, checksum, tokenizer
        v
training/sequence.py          tokenize, reserve-check, window, mask
        v
training/data_loader.py       manifest-order stream, deterministic epoch order
        v
training/model.py (QMModel)   S2 causal transformer (unchanged)
        v
training/objective.py         shifted labels, token-mean loss, accumulation
        v
training/schedules.py         warmup + cosine (stateful)
        v
training/pretrain.py          checkpoint /2 writer, RNG capture
training/manifest.py          run manifest
training/loss_log.py          append-only telemetry
```

New modules in `training/`:

| Module | Responsibility |
| --- | --- |
| `authorization.py` | Production/synthetic dataset gate, refusal codes |
| `sequence.py` | Tokenization, reserved-token safety, window construction, padding |
| `data_loader.py` | Manifest-order streaming, deterministic sampler, resume state |
| `objective.py` | Shifted labels, ignore-index loss, token-mean normalization |
| `schedules.py` | Warmup + cosine schedule with checkpointed state |
| `precision.py` | Device/dtype resolution and refusal |
| `train_config.py` | Versioned configuration schema, validation, hashing |
| `train.py` | The training entry point (`python -m training.train`) |

Reused unchanged: `training/model.py` (the S2 transformer), `training/pretrain.py`
(`save_checkpoint`, `capture_rng_state`, `check_vocab_alignment`),
`training/manifest.py` (run manifest), `training/loss_log.py` (telemetry),
`training/determinism.py` (seeding), `training/checkpoint_schema.py`
(provenance), `training/tokenizer_contract.py` (tokenizer identity), and the
whole v1.2.0 dataset interface.

Supporting files: `scripts/build_synthetic_corpus.py` (generates the labelled
qualification fixture), `configs/train/pretrain_v13.yaml` (production shape),
`configs/train/pretrain_v13_synthetic.yaml` (synthetic template),
`tests/test_v130_pretraining.py` (47 tests).

## 2. Model and tokenizer baseline

Verified against the source, not quoted from history:

| Property | Value | Source of truth |
| --- | --- | --- |
| Architecture | Decoder-only (RMSNorm, RoPE, GQA, SwiGLU), tied embeddings | `training/model.py` |
| Model rung used | S2, `configs/model/code_m3_9m.yaml` | shipped configuration |
| Parameters | 9,359,104 (5822×256 tied embedding = 1,490,432 + 7,868,672) | `configs/model/code_m3_9m.yaml` |
| Model embedding rows | 5,822 | `model.vocab_size` |
| Tokenizer artifact | `tokenizer/qm_code_bpe_v0.json`, 5,822 ids | frozen v1.2.0 corpus |
| Tokenizer effective ids | 5,828 (5,822 + 6 reserved control tokens) | v1.1.0 `CONTROL_TOKENS` |
| Prompt contract | `qm.plain_instruction/1` for the frozen corpus | v1.2.0 manifest |
| Checkpoint contract | `quantsmind.checkpoint/2` | v1.1.0 `checkpoint_schema` |

**Roadmap conflict, recorded.** Roadmap §4 specifies the S3 rung
(16,257,280 parameters, `configs/model/code_30m.yaml`). That geometry requires
a 32,768-wide vocabulary, which exists in no tokenizer in this repository and
is owner decision **D6**. The mission for this version forbids a vocabulary
change, and the roadmap's own §3.4 says the vocabulary "must be fixed before
training". v1.3.0 therefore qualifies the **S2** rung against the frozen
5,822-id tokenizer, and the S3 scale-up remains a separate, D6-dependent step.
The repository's own `configs/model/code_30m.yaml` comment already documents
that this config matches no tokenizer and is an orphan.

**Tokenizer policy.** The v1.2.0 verdict `TOKENIZER_ACCEPTED_WITH_LIMITATIONS`
is honoured as-is: no retraining, no vocabulary change, no embedding resize,
no renumbered specials, no change to the control range, no break to existing
checkpoints.

**The model has 5,822 embedding rows, not 5,828.** The control range
(5,822–5,827) is reserved in the tokenizer but is not present in the S2
embedding table. Pretraining data excludes reserved literals, so no control
id can occur; the sequence builder additionally refuses any id at or above the
model vocabulary, and any control id that is not explicitly authorised. The
widening of the embedding table to 5,828 rows is a separate decision that
belongs with D6.

## 3. Dataset authorization

Training data reaches the trainer only through `training/authorization.py`.
There is no second path, and there is no fallback to a historical corpus.

**Production mode** requires, and refuses without:

| Requirement | Refusal reason |
| --- | --- |
| Manifest exists and has the v1.2.0 schema | `manifest_missing`, `manifest_unreadable`, `manifest_schema_mismatch` |
| The manifest declares class `production` | `synthetic_manifest_refused` |
| `notes.corpus_ready` is true | `corpus_not_ready` |
| At least one approved source | `no_approved_sources` |
| The split is ready | `splits_not_ready` |
| Every artifact checksum verifies | `artifact_verification_failed` |
| The tokenizer file hashes to the manifest's value | `tokenizer_mismatch` |

**Synthetic mode** requires a manifest that declares class `synthetic` and is
labelled synthetic in its notes; a production manifest is refused
(`production_manifest_refused_in_synthetic_mode`) so a qualification run can
never be confused with a production one.

**Status of D1–D5.** The licensing decisions remain unresolved. The shipped
v1.2.0 contract approves zero sources, so `notes.corpus_ready` is false and
production training is refused today. That refusal is the intended behaviour
of an unapproved corpus, and the `configs/train/pretrain_v13.yaml`
configuration exists so the refusal is visible rather than accidental.

## 4. Synthetic qualification mode

`scripts/build_synthetic_corpus.py` generates a corpus locally from a fixed
seed and builds its manifest with `dataset_class: synthetic`. The v1.2.0
pipeline records that class in the manifest notes and computes `corpus_ready`
from it, so a synthetic build is **never** `corpus_ready` and can never be
promoted.

Isolation is enforced in four places:

1. the manifest declares `corpus_class: synthetic` and `synthetic: true`;
2. the authorization gate refuses a synthetic manifest in production mode;
3. the checkpoint provenance records `mode: synthetic` and `synthetic: true`,
   and the run manifest and evaluation report repeat it;
4. the trainer writes to the configured output directory only; no path can
   write into a production run directory.

## 5. Tokenization and sequence construction

`training/sequence.py` is the only place where pretraining text is
tokenized, so the policies are enforced once.

* **Document policy (default).** Each document is tokenized on its own and
  split into windows of at most `context_length` tokens. A window never
  contains two documents, so no attention crosses a document boundary.
* **Packed policy (opt-in).** Documents are concatenated into a fixed-length
  stream. This is more token-efficient but lets a window attend across
  documents, so it must be asked for explicitly: constructing a packed
  builder without `allow_cross_document=True` raises
  `cross_document_packing_not_authorised`. Packed batches are marked
  `cross_document` in the batch and the choice is recorded in the run
  manifest.
* **End-of-document.** The builder appends the tokenizer's `<eos>` id to each
  document. That terminator is inserted by the builder, not present in the
  source, which is why it does not trip the reserved-literal rule.
* **Windows shorter than two tokens are dropped**: they cannot produce a
  single next-token prediction.
* **Padding is suffix-only** and the padded positions are masked with
  `IGNORE_INDEX` in the labels. The S2 model has no padding attention mask,
  but under causal masking a suffix cannot influence the positions before it;
  a test asserts that the valid positions' logits are identical with and
  without the padded tail.

**Reserved-token safety** is revalidated at this boundary:

| Condition | Reason code |
| --- | --- |
| Source text contains a reserved spelling (`<eos>`, `<\|user\|>`, …) | `reserved_literal_in_source` |
| A produced id is in the control range and is not authorised | `unauthorized_control_token` |
| A produced id is at or above the model vocabulary | `token_id_beyond_model_vocab` |

Source text is never rewritten to remove a spelling; the sample is refused.
An id may be authorised explicitly (`authorized_control_ids`), which is how a
future training format can legitimately emit a control token.

## 6. Training objective

`training/objective.py` computes the loss; the model's own loss is not used
because it has no `ignore_index`.

* **Next-token prediction with shifted labels.** A token sequence `t0..tn`
  becomes inputs `t0..t(n-1)` and labels `t1..tn`. The first token has no
  context and the last input has no target; neither is invented.
* **Padding is never predicted.** Labels at padded positions are
  `IGNORE_INDEX` and are excluded from the loss and the count.
* **Loss normalization is token-mean over the accumulation window**: the
  summed per-token loss of the window divided by the number of supervised
  tokens in that window. The window's token count is known before the forward
  pass, so gradient accumulation is numerically equivalent to one larger
  batch (verified to 1e-6).
* **No future leakage.** The model's attention is causal, and a test shows
  that changing the last three tokens of a sequence leaves the earlier logits
  unchanged.
* **Pretraining is plain code.** The canonical chat renderer is not applied.
  Python samples are not wrapped in `<|system|>…<|user|>…<|assistant|>`.
  Instruction tuning is a different objective with a different pipeline
  (v1.5.0); nothing here should be read as its prerequisite being met.

## 7. Optimizer and scheduler

* **Optimizer:** AdamW, configurable `weight_decay` (0.1), betas (0.9, 0.95).
* **Schedule:** linear warmup into a cosine decay with a documented floor
  (`min_ratio`, 0.1). The schedule is a stateful wrapper over the existing
  `training.pretrain.lr_at`, so the v1.3.0 curve and the historical curve
  cannot drift apart. The schedule follows the *planned* run length, so a
  short override or a resume continues on the same curve.
* **Gradient clipping:** global norm clipping at `grad_clip` (1.0), applied
  before the optimizer step.
* **Accumulation:** the number of microbatches per optimizer step is
  `grad_accum_steps`; the effective batch is
  `micro_batch_size × grad_accum_steps`.
* **Step counting:** the optimizer steps once per accumulation window, and
  the run manifest, the checkpoint and the telemetry all report the same
  count.

These are engineering defaults, not claims about optimal hyperparameters.

## 8. Determinism

* `training/determinism.py` seeds Python, NumPy and torch, requests
  deterministic algorithms in warn-only mode, and disables cuDNN benchmarking.
* The window order for an epoch is a pure function of `(seed, epoch)`, drawn
  from a seeded `torch.Generator`.
* The sampler state (epoch, position), the RNG state, the scheduler state and
  the consumed-token count are all checkpointed, so a resumed run replays the
  order the interrupted run would have used.
* Two independent qualification runs over the same synthetic corpus produced
  the same manifest hash and the same loss figures.
* Cross-device bitwise determinism is **not** claimed: only CPU behaviour is
  tested here.

## 9. Checkpoint schema and resume

Checkpoints use the v1.1.0 contract `quantsmind.checkpoint/2` and are written
by the existing `training.pretrain.save_checkpoint`:

| Content | Where |
| --- | --- |
| Model state | `model` |
| Optimizer state | `optimizer` |
| Scheduler state | `scheduler` (extra) |
| Optimizer step | `step` |
| Consumed tokens | `consumed_tokens` (extra) |
| RNG state | `rng_state` (extra) |
| Sampler state | `sampler_state` (extra: epoch, position, seed) |
| Dataset identity | `dataset_identity` (extra: manifest sha256, split, class) |
| Tokenizer identity | `tokenizer_identity` (extra: path, sha256, vocab) |
| Configuration identity | `train_config_sha256` (extra) |
| Model configuration identity | `provenance.config_sha256` |
| Synthetic/production provenance | `provenance.mode`, `provenance.synthetic` |

The eleven v1.1.0 provenance fields are present and validated by
`training.checkpoint_schema.validate_provenance`; the v1.3.0 additions are
extra keys, so a v1.1.0 checkpoint still loads and a v1.3.0 checkpoint still
satisfies the v1.1.0 contract.

Resume refuses, with a specific reason, when the checkpoint is not a `/2`
file, the dataset manifest hash differs, the tokenizer hash differs, the
training configuration hash differs, or the file cannot be read. A resume
restores the model, optimizer, scheduler, RNG and sampler state and continues
on the same learning-rate curve and the same data order. A test trains four
steps in one run and the same four steps as two plus two; the resulting
parameters match to 1e-6.

## 10. Resource safety

Every run has explicit limits, validated before the model is built:

| Limit | Field | Enforcement |
| --- | --- | --- |
| Optimizer steps | `training.max_steps` | loop stops; reason recorded |
| Consumed tokens | `training.max_tokens` | loop stops; reason recorded |
| Wall clock | `training.max_wall_seconds` | loop stops; reason recorded |
| Checkpoint count | `limits.max_checkpoints` | oldest checkpoints removed |
| Output size | `limits.max_output_bytes` | recorded in the run manifest |
| Device / dtype | `precision.device`, `precision.dtype` | resolved or refused |
| Output directory | `training.output_dir` | relative paths only |

`training/train_config.py` refuses an unbounded step or token budget, a
missing limit, a non-relative path in the data, tokenizer, model or output
locations, an unknown mode, a non-AdamW optimizer, a non-positive learning
rate or clip, a context length below two, and any dtype or device outside the
supported set. `training/precision.py` refuses half precision on CPU (the
CPU half kernels do not cover every operation in this model) and refuses a
device the runtime does not have.

Qualification budget used here: CPU only, 40 optimizer steps, context length
256, micro-batch 2, accumulation 2, 33,316 tokens, 64 seconds of wall clock,
120-second subprocess cap. The budget was not raised at any point.

## 11. Evaluation

The evaluation report (`evaluation.json`) records the initial and final
training loss, the first and final validation loss, the best validation loss,
the validation perplexity, the uniform-baseline loss `ln(vocab)`, the token
and window counts, the sequence policy, the device, the stop reason and the
elapsed time. It also carries an explicit `evidence_scope` statement.

Measured on the synthetic qualification corpus (12 generated sources, 48
samples, splits 32/8/8, S2 model, 40 steps, CPU):

| Measurement | Value |
| --- | --- |
| Uniform-baseline loss `ln(5822)` | 8.669 |
| Initial training loss | 8.768 |
| Final training loss | 2.017 |
| First validation measurement | 3.958 |
| Final validation loss | 2.147 |
| Best validation loss | 2.147 |
| Final validation perplexity | 8.563 |
| Optimizer steps / tokens | 40 / 33,316 |
| Windows | 96 |
| Wall clock | 63.8 s |

The run learns the synthetic distribution: the loss falls from the
random-init baseline to 2.02 and the held-out loss follows it to 2.15. That is
the whole claim. It says nothing about Python — the corpus is generated text
with a repeating template, and the model is learning that template.

## 14. Known limitations

* **The S3 rung was not used.** The roadmap's 16,257,280-parameter geometry
  needs a 32,768-id vocabulary, which is decision D6. v1.3.0 qualifies S2.
* **The S2 embedding table has 5,822 rows, not 5,828.** The reserved control
  ids are absent from the model. Pretraining cannot emit them, and the
  sequence builder refuses any id at or above the model vocabulary.
* **The learning evidence is synthetic.** The corpus is generated text with a
  repeating template. Nothing here measures Python ability, and no benchmark
  was run.
* **No published benchmark was available.** The v1.2.0 registry records
  HumanEval and MBPP as unavailable, so contamination screening covers none.
* **Production training has never run**, because no corpus is approved. The
  production configuration exists so the refusal is explicit.
* **Cross-device determinism is not established.** Only CPU is tested.
* **Gradient accumulation equivalence is verified to 1e-6**, not proven
  bitwise.
* **Sequence packing is implemented but not the default**, and the packed path
  is exercised by unit tests only, not by a training run.
* **The wall-clock limit is checked between optimizer steps**, so one very
  long step can overshoot it.
* **The synthetic generator is a fixture generator**, not a data pipeline.

## 15. Dependencies for v1.4.0

1. **An owner-approved corpus (D1–D5, D3).** Without it, v1.4.0 cannot
   measure anything on real Python.
2. **A vocabulary decision (D6).** Either the S2 rung is accepted as the
   production rung, or the vocabulary is resized and the S3 geometry becomes
   reachable, together with the embedding-table change and the compatibility
   handling for existing checkpoints.
3. **A repeat-run variance protocol.** The roadmap requires at least one
   repeat run with a reported spread; the v1.3.0 harness can produce it (same
   configuration, two output directories), but no production-scale repeat has
   been run.
4. **A published benchmark copy.** HumanEval and MBPP must be present
   locally before any capability gate in v1.4.0 can be evaluated.
5. **The v1.2.0 interface stays the only data path.** v1.4.0 must consume
   the same manifests, and the `quantsmind.checkpoint/2` and prompt-contract
   identifiers must not change.
